## Phase 1 decisions (facts engine and checker), 2026-10-08
- Horizon is 12 hours from the current forecast hour. A storm in the current hour counts, even if the hour began before the question.
- Storm = WMO weather code 95-99, or CAPE >= 1000 J/kg with precipitation probability >= 60%. Rain = >= 0.2 mm in the hour with probability >= 50%. These are thresholds I chose; they are not tuned and not validated against outcomes. The walk (Phase 9) is the only field check.
- `turn_by` = return time minus a 90 minute descent assumption (`Trip.descent_min`). It is an assumption, not a measurement. The reply never states the 90.
- A time of day in a question ("by 3") resolves to the next occurrence at or after now; an unmarked hour 1-11 picks the earlier of AM and PM that is still ahead.
- Number rule: a number is the digits plus the unit glued to it, compared as one string. `55 km/h`, `55mph` and a dropped minus sign all count as invented. A number in the hiker's question is allowed as written, and a clock time in the question also allows its 24-hour form.
- Required facts: a question's intents name groups of fact keys; the reply must state at least one fact of each group that exists. A group with no existing fact is not demanded.
- Template go/no-go: "No-go" when a storm starts at or before the target time (or the trip car time); "Caution" for a later storm or gusts >= 60 km/h; otherwise "Looks OK". It says nothing about rain, cold or daylight in the verdict.
- Elevation comes in the forecast response, so there is no separate elevation module. `locate.py` (place name to coordinates) moves to Phase 5 with the `TRIP` command.
- Tests that need a storm use a synthetic forecast; the 20 frozen real forecasts have no thunderstorm, so storm paths are covered by editing one hour of a real forecast.

## Phase 2 decisions (thin end-to-end path), 2026-10-09
- **Endpoint.** The Tinker chat endpoint is unusable for Qwen3-8B here: `/chat/completions` returned empty content at `max_tokens=200` both by default and with `chat_template_kwargs.enable_thinking=false`, finish reason `length` (thinking appears to consume the budget). The `/completions` endpoint with a hand-rendered prompt works: the Qwen chat format with the assistant turn opened as `<think>\n\n</think>\n\n`, `stop=["<|im_end|>"]`. That is the cookbook's `qwen3_disable_thinking` shape, so SFT in Phase 4 can train on the exact string the server sends. One function (`onebar/model/prompt.py:render`) builds it for serving, data generation and training.
- **Sampling.** temperature 0, `max_tokens` 120, 20 s timeout, no SDK retries. The one retry is the pipeline's, and it changes the prompt (the rejected draft and the reasons, in plain words, never internal fact keys).
- **Failure policy.** A model error (timeout, HTTP error, empty text) goes straight to the template with no retry, so a dead endpoint costs one timeout, not two. A checker failure gets exactly one corrected retry, then the template. The template is checked too; its verdict is in the trace.
- **Checker change (additive, found by this run).** The first live run passed `No thunderstorms today. First thunderstorm hour: 13:00.` The Phase 1 checker verified numbers, length and fact presence, not polarity. Added `onebar/check/polarity.py`: a reply fails with `contradiction:storm|rain` when it denies an event the facts contain without a time qualifier, or mentions an event the facts rule out without negation. Verified by planted contradictions (16 flagged) and by the 3,360-case template test still passing.
- **Known gap, not fixed.** A qualified denial is not judged: `No storm by noon.` passes even when the storm starts at 11:00 (q12 below). Judging it needs time arithmetic against the question's target. The tuned model's training data inherits this gap, so Phase 3 reports it as a limit rather than hiding it.
- **Phase 2 exit run (`scripts/run_phase2.py`, `eval/results/phase2_base.json`).** 20 hand-written questions (`eval/phase2_questions.jsonl`) on the 20 frozen real forecasts at 10:20 local, live `Qwen/Qwen3-8B` base model, current checker. Four of the 20 (q10, q12, q17, q19) have a synthetic thunderstorm hour written into the forecast, because none of the frozen real forecasts holds one.
  - Passed the checker on the first try: 12/20. After one retry: 18/20. Template fallback: 2/20. Model errors: 0.
  - Latency per question including any retry: p50 1.24 s, max 4.87 s.
  - Quality of the passes, read by hand: poor. Several passing replies echo the fact labels (`highest chance of rain in the next hours: 100%`), dump unrelated facts (q07 lists nine values), or answer `Yes.` to a question that needs a verdict. The checker accepts them because every number is real and the required facts are present. The pass rate overstates usefulness. Phase 4's win has to show in the replies, and the eval table must say what "pass" does not measure.
  - n = 20 is a smoke test, not a benchmark. The Phase 3 test set carries the real baseline.

## Phase 3 decisions (dataset and eval harness), 2026-10-09
- **Locations.** 1,603 real OSM summits, huts and trailheads from 37 of 43 planned mountain regions (`data/locations.jsonl`). Six Overpass regions timed out repeatedly (504) and were dropped rather than waited for; the code is in `onebar/dataset/locations.py`, quota 45 per region, seeded. Huts and trailheads are drawn ahead of peaks, so peaks do not crowd them out.
- **Facts.** Every fact set is cut from a past forecast issued by Open-Meteo's historical forecast API (one 10-day window per location, cached under `data/cache`, not committed). 4,809 situations, 3 per location, on distinct days, ask times 05:00-17:59 local, 47% with a trip. Storm-ahead is 8.5% of situations even with steering (half of situations are steered to an hour with a storm ahead when the window has one): storms are rare in real forecasts. The model sees few storm cases; the eval must be read with that in mind.
- **Split.** By 0.5 degree map cell, hashed, not by row and not by single location, so two neighbouring summits with the same weather cannot straddle train and test. Test 414 rows, frozen in `eval/test.jsonl`.
- **Questions.** 44 seed shapes in hiker register; 58% of the 60% sent to the paraphraser (Qwen3.5-397B) were accepted, so 34% of rows are paraphrased. A paraphrase is accepted only if it keeps every number, the same intents and the same parsed target time (so the stored facts equal what serving computes). Rejected ones fall back to the seed.
- **Teacher.** Chosen by measurement on 50 train questions, 4 candidates each, checker pass plus a "reads naturally" filter (no fact-label echo): Qwen3.5-397B-A17B 44/50, GPT-OSS-120B 41/50 (`eval/results/teacher_choice.json`). The first teacher prompt scored 22/50 because the checker demands storm status and gusts on go/no-go and turn-around questions; the prompt now says so. The endpoint ignores `n`, so each candidate is its own call.
- **Credit ran out.** Tinker returned HTTP 402 (billing status) after 2,475 of 4,395 train/val questions had teacher candidates. Those 2,475 gave 1,824 train + 295 val rows (2,119, above the 2,000 target). The other 1,920 questions have no teacher answer. They are the tail of a region-ordered file, so **training covers 21 regions (Europe, Africa, Nepal) and the test set has 5 regions with no training data** (Ladakh, NZ Southern Alps, Peru, Tasmania, Cascades). That makes the test stricter than planned, not easier. Finishing the draws (`python scripts/build_dataset.py teacher`, resumes from cache) fixes the coverage; it needs credit.
- **Not run: the large-model eval row.** It needs the API. `make eval` produces template and base; `python eval/run_eval.py --system large` adds the large row once billing is restored.
- **Two checker fixes found by this phase.** A literal "0%" now counts as a negation ("Rain chance is 0%" no longer contradicts a no-rain fact). The earlier polarity gap (qualified denials) remains.
- **Base numbers on 414 test questions** (`eval/TABLE.md`): 56.8% pass the checker on the first try, 82.9% reach the user from the model after one retry, 17.1% fall back to the template, 73.1% required-fact coverage, mean 64 septets (template 46), 1.64 s p50, $0.00011 per answer. These are the numbers Phase 4 must beat.

## Phase 4 decisions (Tinker SFT), 2026-10-09
- **Recipe.** LoRA rank 32 on `Qwen/Qwen3-8B`, 3,290 train rows, 2 epochs, batch 32 (206 steps), learning rate 2e-4 decaying linearly to 10%, cross-entropy on the reply and the end-of-turn token only, loss normalised to a per-token mean. The training prompt is the exact string the pipeline sends at serving (`onebar/train_data.py:prompt_for`, tested byte for byte). Code: `train/sft.py`. These hyperparameters were chosen once, not searched: the budget allowed one run.
- **Checkpoint choice.** Validation first-try pass on 150 held-out val questions: epoch 1 96.7%, epoch 2 98.7%. Epoch 2 is the tuned model (`eval/results/sft_run.json`). Val shares the teachers' distribution with train, so the number that counts is the frozen test set below.
- **Cost.** Training charged $0.86 (976,888 tokens per epoch at the published $0.44 per million); validation and the tuned eval about $0.1. Whole-grant ledger total after Phase 4: $3.68 of $10, under the $5 ceiling set for this work. The ledger cap was raised from $3.20 to $4.60 for this phase only, because training spend counts toward it.
- **Result on the 414 frozen test questions** (`eval/TABLE.md`): first-try checker pass 98.1% (base 56.8%, larger model 57.2%); invented numbers 0.0% (base 1.4%); contradictions 0.0% (base 3.6%); required-fact coverage 99.1% (base 73.1%); 100% of replies came from the model with no template fallback; mean 47 septets (base 64); cost $0.000069 per answer (base $0.00011, larger $0.00027), because the tuned model needs no retry and a shorter prompt effect: 1.02 calls per answer against 1.43.
- **Read this with care.** (1) The checker measures structure: numbers, length, required facts, storm/rain polarity. It does not measure whether a qualified claim ("no storm by noon") is right or whether the advice is wise. The tuned model learned the teachers' style, so it inherits their blind spots. (2) The student was trained to pass the same checker that scores it. The gain is real for what the checker covers; it is not independent proof of forecast skill. (3) Latency p95 in the sequential 40-question pass was 6.2 s against p50 1.19 s; the p95 is likely endpoint variance, one run, not a trend. (4) One training run, no seeds, no confidence interval.
- **Not done.** 4b RL was skipped to protect the credit; the SFT gain is large enough that RL has little headroom on this checker. 4c Hugging Face export needs a write token (`HF_TOKEN` is empty in `.env`) and the adapter download; the model card facts are in this file and `eval/TABLE.md`. The tuned weights live on Tinker at the path in `.env` (`ONEBAR_MODEL`), checkpoint named `onebar-sft-e2`.

## Phase 5 decisions (Temporal TripWorkflow), 2026-10-09
- **Temporal target.** Self-hosted dev server (`.tools/temporal.exe server start-dev`, the CLI's SQLite-backed server), not Temporal Cloud: no key needed, which also answers the open "Cloud trial or self-hosted" question from the plan. The same code runs against Cloud by setting `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE` and `TEMPORAL_API_KEY`; the worker currently reads the first two only (an API-key connection is not wired).
- **One workflow per sender**, id `onebar-<normalised sender>`. Messages arrive as a signal (`message_received`) through signal-with-start (`onebar/temporal/starter.py`), so the first message starts the workflow and later ones join it.
- **Dedupe is in the signal handler**: an id already in `seen` is dropped before it is queued, so a redelivered message gets no second reply. Reply sends also carry the idempotency key `reply:<message id>`; alerts carry `alert:<trip id>`. The outbox sender writes a key once and remembers it across restarts (the file is the key store).
- **Activities.** `resolve_trip` (place to coordinates, UTC offset from the forecast, deadline), `answer_question` (forecast, facts, draft, check, template fallback), `send`. Deviation from the plan, on purpose: `locate`, `facts` and `draft` are one activity per question rather than three, so the ~70 KB forecast never enters the workflow history. The model timeout (20 s) and the corrected retry live in the pipeline. Open-Meteo errors are retried with exponential backoff, 4 attempts; a non-retryable error (forecast does not cover the time) fails fast. After the retries the hiker gets "Forecast unavailable right now."
- **The overdue timer** is a `wait_condition` with a timeout equal to return time plus grace (default 30 minutes, `ONEBAR_GRACE_MIN`), measured on the place's clock (UTC offset from the forecast). A return time that has already passed today means tomorrow. OUT clears the trip and so cancels the alert. If sending the alert fails after its retries, the workflow tries again every 5 minutes; the key stops a late success from doubling it.
- **Continue-as-new** after 100 messages (configurable per workflow), carrying the trip, the seen-id set and the timer state. Tested with a limit of 3: the trip, the dedupe set and the alert all survive a rollover.
- **Commands** (`onebar/commands.py`): TRIP, OUT, FORGET, HELP, otherwise a question. A command word inside a question stays a question ("outside?", "help me, is it safe"). Inbound text over 500 characters is refused. Contact must be an email or a phone number.
- **Delivery is not real yet.** Replies and alerts are written to `data/outbox.jsonl`. Email and web delivery are Phase 6. Nothing in Phase 5 sends a real message to anyone.
- **Tests** (`tests/test_temporal.py`, Temporal's time-skipping server): overdue trip alerts exactly once; OUT before the deadline sends none; the same id twice gets one reply; a flaky sender is retried and the alert lands once; forecast outage gives a clear reply; FORGET ends the workflow and wipes state; continue-as-new keeps state. Two defects were planted to prove the tests can fail (dedupe off, OUT not clearing the trip); both were caught.

## Phase 6 decisions (channels), 2026-10-09
- **Email uses the owner's existing Gmail, so the poller is built to stay out of the way.** It opens the mailbox read-only and fetches with `BODY.PEEK` (a test asserts no `STORE`, `COPY` or `EXPUNGE` and no plain `BODY[]`). It searches only mail addressed to the plus-alias (`name+onebar@gmail.com`, which Gmail delivers to the normal inbox) from the last 3 days. It skips automated mail (Auto-Submitted, Precedence, List-Id, bounces, no-reply senders), anything without a Message-ID, and the owner's own address unless `--allow-self` is passed. Each mail is processed once, by IMAP uid and by Message-ID, remembered in `data/email_seen.json`. At most 20 mails per pass; 10 messages per sender per 10 minutes, then silence.
- **Replies can never loop.** Every reply carries `Auto-Submitted: auto-replied` and `X-OneBar`, and the parser refuses both (a test feeds our own composed reply back into the parser). Replies go out in thread (`In-Reply-To`, `References`, `Re:` subject). Body is the checked text plus, when a trace exists and `ONEBAR_PUBLIC_URL` is set, one footer line linking the trace page.
- **At-least-once for alerts.** The email sender records a key only after SMTP accepts the mail, so a crash can repeat a message but never lose one.
- **Phone contacts are refused** (`TRIP ... CONTACT +44...` gets "CONTACT must be an email address") because there is no SMS channel. Twilio stays a stretch item and is not started.
- **Web API** (`onebar/channels/web_api.py`): `POST /api/message`, `GET /api/reply/{id}`, `GET /api/trace/{id}`, `GET /api/health`. Messages over 500 characters get 413; session ids are validated; limits are 10 messages per 10 minutes per session and 30 per IP; a Temporal outage is a plain 503 with no internals; OpenAPI docs are off. Replies are stored by an unguessable message id, traces by a hash of it, and a trace never contains the sender's address or session id (tests check both).
- **Security items from the plan, status:** rate limit per sender (done, email and web), max inbound length (500, done), no secrets in logs (the poller logs counts and exception type and file:line only, never addresses or text), trace page shows no sender address (done). `ecc:security-review` on the public endpoints has not been run; run it before the deploy in Phase 8.
- **Latency, measured, and what it does and does not show.** Four live runs of `scripts/e2e_email.py` (TRIP plus three questions, real Gmail, real Temporal dev server, tuned model). The sender was the owner's own address, because that is the only sender available here; so the "fresh outside address" exit test in the plan is **not** satisfied as written. Findings:
  1. First run, 62 to 105 s. Timestamps showed pickup 1-16 s, processing 5-16 s, and 35-75 s more before the reply was visible in the mailbox.
  2. A persistent IMAP connection and 5 s polling did not help (a fresh connect cost 4.4 s per pass, but Gmail itself made a self-sent mail searchable only 10-19 s after sending).
  3. The real controllable cost was the tuned adapter going cold: 1.0 s warm, 3.1 s after 20 s idle, 6.6 s after 45 s idle. The worker now pings the model every 15 s (`ONEBAR_KEEPALIVE_S`, 0 turns it off; about $0.003 per hour through the ledger). That also explains the 6.25 s p95 in the Phase 4 eval.
  4. Final run: send to reply accepted by SMTP, 15.2 s, 23.7 s, 13.0 s. All under 30 s. Time until the reply was visible in the owner's own mailbox was still 55-72 s in that run: Gmail delivering a message from the account to itself. I could not measure delivery to an outside address and do not claim it.
- **Forecast cache.** Forecasts are reused for 10 minutes per place (2 decimals) inside the worker, so a follow-up question skips the network call. The outage test turns the cache off to see the outage.
- **Not done:** Twilio SMS, inReach parsing (stretch, unverified), deploy. The trace footer link points at `ONEBAR_PUBLIC_URL`; the page it opens is the Phase 7 UI, which does not exist yet.

## Phase 7 decisions (web UI), 2026-10-09
- **Stack.** Vite, React 19 and TypeScript (strict), CSS Modules with one `tokens.css`, `motion` for the one animated sequence, react-router. It builds to static files that the FastAPI service or a reverse proxy can serve next to `/api`, so the droplet needs no Node process. No Tailwind and no component kit.
- **Routes.** `/` Ask (a handset beside the audit sheet), `/results`, `/how-it-works`, `/trace/:id` (the audit sheet alone; this is the page the email footer link opens).
- **What the first screen shows.** Before the visitor has asked anything, the audit sheet shows the first recorded example, labelled "A recorded example, checked", so the map, hour strip, number rows and checks are visible at once. Recorded examples are three real rows of the frozen test set (`scripts/make_web_examples.py` writes `web/src/data/examples.json`); a replay in the thread is captioned "Recorded example from the test set. Not live." Nothing on the page is invented sample text.
- **The proof is the interface.** Every number in a reply is a button. Hovering or focusing one draws a single leader line from it, along the gap under its text line and across the gutter, to the row that says which forecast fact it was read from, and lifts the forecast hour it refers to. One line at a time, because several lines from numbers on the same text line cannot be routed without crossings (found by rendering three prototypes). The line shows only at 1024 px and up; below that the row highlights instead.
- **The signature moment** (a fresh reply gets audited, about one second): length meter fills, each number is checked in turn (at most four animate), the five checks tick, the verdict line appears and is announced politely. A reply that is not new, and a visitor who prefers reduced motion, get the end state at once with the same words.
- **Base model comparison.** A Tuned/Base toggle shows the base model's draft for the same question with the checker's own verdict (for the ridge example: 241 characters, over the limit, and a rain claim the forecast contradicts). This needed the backend to keep the base draft in the trace: `onebar/channels/traces.py` now stores `hours`, `baseline` and `place`, and the worker makes the baseline call with `Qwen/Qwen3-8B` (`ONEBAR_COMPARE=0` turns it off; about $0.0001 per reply).
- **Terrain.** Contour lines are computed in the browser from an Open-Meteo elevation grid (marching squares, no map library, no tiles). The recorded examples ship with theirs. If the elevation call fails the sheet says so in words and everything else still works.
- **Backend change found by the UI work: PLACE.** A web visitor has no trip, and a question with no trip was read in UTC, so "by 3" meant 3 pm UTC wherever the hiker was. Added a `PLACE <name or lat, lon>` command (it sets where the hiker is without starting a trip) and the workflow now keeps the last known UTC offset. Tests plant the old behaviour and fail on it. The picker's quick places go through the same command, so the geocoder is exercised live.
- **Theme.** Light "map paper" and dark "night map", both designed, following the system until the visitor switches. `?theme=light|dark` pins one visit (used for screenshots and scoring, because headless Chrome defaults to dark).
- **Measured, not eyeballed.** `web/scripts/palette-check.mjs`: every text pair at least 4.5:1 and every shape at least 3:1 in all three theme blocks, role hues at least 35 apart in CIE Lab, accent chroma at least 5 times any surface's (5.2). The two dark token blocks are checked to be identical.
- **Known gaps, stated.** (1) The ui-score tool counts a tinted dark ground as an "accent" by HSV saturation, so the dark theme scores 0/10 on its accent budget by construction; the light theme is the meaningful number. (2) The tool flags `multiple-accents`: the page uses a blue data hue, a red reject hue and an ochre terrain hue next to the one teal accent, on purpose, each with a job. (3) The base-model draft only exists for replies made while `ONEBAR_COMPARE` is on. (4) Live traces carry coordinates but no place name, so the Ask page labels the map with the name the visitor set and `/trace/:id` says "your place". (5) The JS bundle is 571 kB (199 kB gzip); routes are not split yet.

## Deploy fix: forecasts on Render, 2026-10-10
- **Symptom.** On https://onebar-v46s.onrender.com every `PLACE` (by name or by coordinates) answered "Forecast unavailable right now" after 50-64 s, while the same Open-Meteo URLs answered 200 from a laptop. 64 s is the 429/5xx path exactly: four workflow attempts, each making four HTTP tries with 1.5/3/4.5 s sleeps. A network error fails in about 14 s and a hang in about 94 s. Open-Meteo counts its free quota per IP, and Render's shared outbound IP is over it before OneBar makes a call (open-meteo/open-meteo discussions #853). The cause is inferred from timing; Render's logs were not read.
- **Fix.** The web page fetches the same two Open-Meteo URLs itself (geocoding for `PLACE`/`TRIP`, the forecast for the place and for every question) from the visitor's own connection, and sends them with the message as a `hint` (`web/src/lib/openMeteo.ts`). The API checks the shape and keeps only what the facts engine reads (`open_meteo.clean_forecast`: coordinates within 0.25 degrees of the request, every hourly column the right length and numeric or null, hour and sunset stamps well formed, offset within 14 h). It files the hint under that session's workflow id (`onebar/channels/hints.py`, 30 minute life). The worker uses a matching hint before its own call and never puts it in the shared forecast cache. So a visitor can only change the facts in their own replies, and the checker still traces every number to the forecast it was given. Email still fetches on the server.
- **Proof.** Local stack (Temporal dev server, worker, API serving the built UI, tuned model) with every server-side Open-Meteo call forced to HTTP 429. Control without a hint: "Forecast unavailable" after 52 s and 16 refused calls, the same as Render. Headless Chrome on the new build: place set in 2.1 s, then "how windy is it going to get?" answered by the tuned model on the first try ("Gusts up to 18km/h. No storm expected.", 1 of 1 numbers traced), with the base-model comparison and zero server-side Open-Meteo calls. `tests/test_hints.py` plants 13 malformed forecasts; all are refused, and a validator that refuses nothing turns all 13 red.
- **A lost place is restored.** Render's free plan has no disk, so a restart forgets every visitor's place while their browser still shows it. When the server replies "No place yet." and the page holds the confirmed coordinates, the page sends `PLACE lat, lon` once (keeping the name the hiker chose) and asks again.
- **Budget cap on Render raised from 3.2 to 4.6.** The container seeds its ledger from `data/spend.json`, which already holds $3.68, so at 3.2 every live reply was refused by the cap and written by the template. 4.6 is the value used for Phase 4 and keeps the whole grant under the $5 ceiling set above. The ledger has no disk on Render either, so the cap holds per container life, not across restarts. Serving costs about $0.00018 per reply (tuned plus base) plus about $0.003 per hour of keepalive while awake.
